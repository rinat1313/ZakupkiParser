01. API И ОФИЦИАЛЬНЫЕ КАНАЛЫ ДАННЫХ ЕИС
=======================================
Вопрос TASK: можно ли не парсить HTML, а использовать REST API?


1. ЧЕСТНЫЙ ОТВЕТ
----------------
Единого открытого REST API zakupki.gov.ru «для любого желающего» нет.
Есть набор каналов с разным доступом. Для физлица / стартапа без КЭП юрлица
основной путь — публичный веб (HTML + printForm XML + RSS).


2. ОФИЦИАЛЬНЫЕ / ПОЛУОФИЦИАЛЬНЫЕ КАНАЛЫ
--------------------------------------

2.1. SOAP API — int44.zakupki.gov.ru
  - Документация, XSD, методы вроде getCustomerDocs — есть.
  - Требуется квалифицированная ЭЦП юридического лица.
  - Для физлица / без КЭП — не подходит.
  - Имеет смысл, когда появится юрлицо и официальная интеграция.

2.2. FTP с XML-выгрузками
  - Раньше: ftp://ftp.zakupki.gov.ru (в т.ч. free:free).
  - ЗАКРЫТ с 1 января 2025 (оптимизация инфраструктуры).
  - Статьи 2023 года про BaseX+FTP — устаревший источник bulk-данных.
  - В новых планах FTP не закладывать.

2.3. Портал opendata.gov.ru
  - Каталог «открытых данных» (Реестр контрактов 44-ФЗ и т.п.).
  - На практике часто нет прямых ссылок на скачивание.
  - Кнопка «API» уводит обратно на ЕИС.
  - Как источник данных не рассчитывать.

2.4. Интеграционный сервис getDocsIP (сервисы отдачи ЕИС)
  - Выдача архивов XML по фильтрам (44 и 223).
  - Нужен текстовый ТОКЕН сервисов отдачи (не USB-ЭЦП).
  - Open-source пример: https://github.com/longhairdude/zakupki-gov-ru
  - Статья: https://habr.com/ru/articles/1044720/
  - VPN часто ломает доступ.
  - Если токен получить — лучший bulk-канал без КЭП юрлица.


3. ПУБЛИЧНЫЕ ЭНДПОИНТЫ БЕЗ ЭЦП (РЕКОМЕНДУЕТСЯ)
---------------------------------------------

3.1. Печатная форма XML по номеру извещения
  https://zakupki.gov.ru/epz/order/notice/printForm/viewXml.html?regNumber=0134300097526000797

  Параметры (по Stack Overflow / практике):
    regNumber     — номер извещения (предпочтительный)
    noticeId      — внутренний id (хуже: раньше брали из имён FTP-файлов)
    printFormId, protocolId, noticeCancelId — для других форм

  Плюс: структура XML стабильнее HTML-вёрстки.
  Минус: не всё (файлы вложений, часть UI-полей) может быть только в HTML.

3.2. HTML-печатная форма
  /epz/order/notice/printForm/view.html?regNumber=...
  /epz/order/notice/printForm/viewByVersionNumber.html?regNumber=...&versionNumber=1&qualifier=regNumberAndVersion

3.3. RSS по номеру
  /epz/order/notice/rss?regNumber=0134300097526000797
  Удобно для «шапки» / мониторинга изменений.

3.4. Обычные HTML-страницы ЕИС (см. 02–05)
  Поиск, карточка, документы, журнал — всё SSR.


4. СТОРОННИЙ REST (ПОСРЕДНИК)
-----------------------------
Пример из SO: gosplan
  https://dev.gosplan.info
  Песочница: https://fz44test.gosplan.info
  Документация: https://quarter18.gitbook.io/gosplan/

  Примеры:
    GET /api/v1/purchases/{regNumber}
    GET /api/v1/plangraphs2020/{planNumber}

  Плюсы: готовый JSON.
  Минусы: зависимость от третьей стороны, покрытие/актуальность не = ЕИС,
  для прод-системы нужен свой путь к первоисточнику.


5. РЕКОМЕНДУЕМАЯ ПОЛИТИКА ДОСТУПА
---------------------------------
Приоритет:
  1) Есть токен getDocsIP → bulk/search через него; деталка/файлы — XML+HTML.
  2) Есть КЭП юрлица → SOAP int44 для официальной интеграции.
  3) Иначе → HTML + printForm XML + RSS + filestore, со строгим rate limit.
  4) FTP не использовать. opendata.gov.ru не считать источником.
  5) gosplan — опциональный ускоритель, не единственный source of truth.


6. ВЫВОД ДЛЯ TASK
-----------------
«Полностью отказаться от парсинга» нельзя, если нет КЭП/токена.
Можно СНИЗИТЬ объём HTML-парсинга:
  - поиск: HTML results (или getDocsIP);
  - карточка: сначала viewXml.html?regNumber=...;
  - файлы: всё равно HTML вкладки документов + filestore uid;
  - в БД хранить сырой XML/HTML + нормализованные поля.
